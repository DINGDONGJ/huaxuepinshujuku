# 优化建议

这份文档基于当前仓库实际代码、数据结构和运行方式整理，重点不是罗列所有问题，而是帮助后续优化更有顺序。

## 一句话结论

项目已经具备可用的业务能力，但当前主要问题集中在：

- 安全边界薄弱
- 配置和密钥管理粗放
- 查询链路有明显重复和性能浪费
- 前后端都已经出现“大单文件”问题
- 可运维性和可测试性不足

如果后续要长期维护，建议先做“稳态化”，再做性能和工程结构优化。

## 必须优先处理

### 1. 收紧接口权限和运行模式

当前系统没有登录和权限控制，但却开放了高风险接口：

- 导入数据
- 删除化学品
- AI 相容性分析

同时服务默认仍以调试模式运行。

建议：

- 关闭生产环境 `debug=True`
- 给管理类接口加最小认证
- 至少区分“只读接口”和“管理接口”
- 不再直接把原始异常信息返回给前端

### 2. 把所有配置迁到环境变量

当前数据库连接和部分 AI 配置仍是硬编码。

建议：

- 把数据库 host、user、password、database 全部迁到环境变量
- 把 AI_BACKEND、OPENAI_API_KEY、OPENAI_API_BASE、OPENAI_MODEL 也统一迁出代码
- 提供一个 `.env.example` 或配置说明文档

### 3. 清理明文密钥和敏感工具

仓库里出现过明文 API Key 和硬编码密码。

建议：

- 立刻移除仓库中的明文密钥
- 认为已提交过的密钥已经泄露，执行轮换
- 清理只用于临时测试的辅助脚本

### 4. 统一数据库表名大小写

当前建表脚本和运行代码存在表名大小写混用。

这在 Windows 上未必立刻报错，但在 Linux/MySQL 某些配置下会失败。

建议：

- 统一使用一套表名
- 建表脚本、运行代码、导入脚本、文档保持一致

## 建议近期处理

### 5. 拆掉 N+1 查询

多化学品接口目前是“循环查数据库”，每个化学品要发多次 SQL。

影响：

- 化学品数量一多，响应时间线性变差
- 数据库连接占用升高

建议：

- 使用 `IN (...)` 一次取回多条基础信息
- 一次性查询多个化学品的章节内容
- 在 Python 中完成分组和组装

### 6. 优化搜索链路

当前搜索大量依赖 `%LIKE%`，随着数据量上升，性能会继续下降。

建议：

- 给自动补全和列表查询增加更明确的索引利用策略
- 对 `limit` 做上限保护
- 评估是否逐步引入全文检索或专门搜索索引
- 让语义搜索成为真正的补充路径，而不是掩盖主搜索性能问题

### 7. 统一数据库连接和异常处理

当前每个接口都手工开关连接，异常路径不够稳定，容易出现资源释放不一致。

建议：

- 封装统一的数据库访问层
- 使用上下文管理或统一 `try/finally`
- 后端日志和前端错误消息分离

### 8. 让语义搜索按需加载

语义模型加载是重操作，目前初始化时就尝试导入和实例化。

建议：

- 改成懒加载
- 或者拆成独立任务/独立服务
- 构建索引后记录版本，避免旧索引长期混用

## 中期优化方向

### 9. 拆分后端结构

当前核心逻辑集中在一个大文件里，后续维护成本会越来越高。

建议按下面方式拆分：

- `routes/`
- `services/`
- `repositories/`
- `models/` 或 `schemas/`
- `utils/`

一个实用的第一步是先把这些逻辑拆出去：

- 搜索
- 法规匹配
- 相容性分析
- 文件导入

### 10. 拆分前端模板

`templates/index.html` 已经承担了页面结构、样式、交互、PDF 查看器、搜索逻辑和管理面板。

建议：

- 把 CSS 拆到独立静态文件
- 把 JS 拆成模块
- 把页面区域按功能拆成更清晰的模板或组件

### 11. 给导入链路增加严格校验

当前导入接口对 JSON 的验证偏弱。

建议：

- 校验必填字段
- 校验章节编号范围
- 校验 CAS 格式
- 校验图片字段结构
- 增加“仅校验不入库”的预检查模式

### 12. 重构 AI 相容性分析

AI 分析目前更像实验性能力，不适合直接承担稳定业务判断。

建议：

- 先保留规则分析为主路径
- AI 作为补充说明，而不是唯一结论来源
- 给 AI 结果加结构校验和失败降级
- 考虑异步化，避免长时间占用 Web 请求线程

## 工程治理建议

### 13. 补最小测试集

当前项目基本没有测试保护。

建议先补最小集合：

- 搜索接口 smoke test
- 法规匹配 smoke test
- 导入接口 JSON 校验 test
- 章节提取函数单元测试

### 14. 建立数据和脚本治理规则

仓库里历史脚本、重复目录和临时文件较多，容易让新接手的人误判入口。

建议：

- 保留“唯一官方入口”
- 把历史脚本迁移到 `docs/archive` 或直接清理
- 明确哪些文件是缓存、哪些是源数据、哪些是可再生成物

### 15. 给大数据文件增加版本策略

当前仓库里有大量 JSON、PDF 和索引文件。

建议：

- 明确哪些文件应该进 Git
- 哪些文件应改为下载式或构建式
- 对生成文件建立命名规范和更新流程

## 推荐执行顺序

如果按性价比排序，我建议这样推进：

1. 关闭 debug，迁移配置，清理密钥
2. 统一表名大小写
3. 收敛导入/删除接口权限
4. 修复连接管理和异常处理
5. 拆掉多化学品接口的 N+1 查询
6. 重建语义搜索和数据脚本边界
7. 拆后端模块
8. 拆前端模板和脚本
9. 补测试

## 最后建议

这个项目最适合的改法不是“大重写”，而是按下面原则持续收敛：

- 先稳住边界
- 再消掉热点瓶颈
- 最后逐步重构结构

这样风险最低，也最适合已经在运行中的系统。
